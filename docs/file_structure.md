# Repository Layout and Test/CI Setup

## Key Components

### `bib-detector/`
This directory contains the local bib detection client that runs on a laptop or other device at the race finish line. It
uses a trained YOLOv5 model (`best.pt`) to detect runner bib numbers from video footage. The detection logic
(`bib-detector.py`) integrates with a local image capture script and optionally posts results to a backend API
(`website_api.py`). A dummy implementation is also provided for testing purposes.

### `running/`
This is the main Django web application. It includes all server-side logic such as views, models, templates, and forms.
It also contains a subdirectory (also named `running/`) which holds configuration files (`settings.py`, `asgi.py`,
`wsgi.py`, and `.env`) needed to run the Django project. The `db.sqlite3` file is the default local database used during
development. A `manage.py` script serves as the primary command-line interface for the app.

### `docs/`
Documentation and planning resources are stored here. This includes the software architecture, database schema, legal
and ethical considerations, and a Gantt chart for project management. Visual materials (e.g., `runningsysdiag.png`) and
presentation files are also located in this directory.

### `scripts/`
Contains standalone utility scripts used during development or deployment. For example, `image-upload.py` may be used to
upload annotated images to the website, to simulate results generated by the CV script.

### `tests/`
This folder include frontend end-to-end tests written with Playwright.

### `logs/`
Houses runtime application logs, useful for debugging and auditing during development and testing. The file `app.log`
captures server-side events or errors.

### Other Notable Files
- **`README.md`**: High-level project overview and instructions for setup and usage.
- **`LICENSE`**: The legal license for the project.
- **`.gitignore`**: Specifies files and directories to be excluded from version control.
- **`requirements.txt`**: Lists Python dependencies for the Django backend.
- **`package.json` & `package-lock.json`**: Define Node.js dependencies used for Playwright testing.
- **`playwright.config.ts`**: Configuration file for Playwright.
- **`file_structure.txt`**: Snapshot of the directory layout.


## Test and CI Setup

### Unit & Integration Testing

To run backend Django tests:

```bash
cd running
python manage.py test
```

### UI Tests (Playwright)

Ensure dependencies are installed:

```bash
npm install
```

To run all Playwright tests:

```bash
npx playwright test
```

To view test reports (after test run):

```bash
npx playwright show-report
```

### Continuous Integration

CI is handled through GitHub Actions. To simulate locally, install [act](https://github.com/nektos/act) and run:

```bash
act
```

There are two continuous integration workflows — `django.yml` and `playwright.yml` — designed to automatically validate
changes submitted via pull requests to the main branch. The `django.yml` workflow focuses on backend integrity by setting
up a Python environment, installing project dependencies, running database migrations, and executing Django unit tests.
This ensures that core application logic remains functional and stable after every proposed change. The `playwright.yml`
workflow is dedicated to frontend end-to-end testing using Playwright. It sets up a Node.js environment, installs
browser dependencies, and runs automated tests to verify the user interface and interactions behave as expected. Both
workflows are designed to surface errors early and support artifact uploads for further inspection.
